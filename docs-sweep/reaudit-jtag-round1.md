## Extra code-owner candidate — `XCOMMENT` stall trap

The docs now state the behaviour accurately: `xsvf.md:100-102` says the XCOMMENT loop "keeps reading `0xFF` and does not end until the board is reset", and `edge-cases.md:74` says "player does not return; `0x0F` is ignored \| reset the board." That matches the recorded code path (`readByte()` serving `0xFF` forever after `xsvf_stream_stalled`, with `xsvfDoXCOMMENT()` looping while the byte is non-zero). The warning is correct and the recovery is the only one available. The firmware defect remains for the code owner; the docs do not overstate the recovery.

## New / residual problems (max 5)

1. **[minor] `wiring.md:44` drops the action byte.** "the host sends feature `0x02 0x02`" reads as command + feature, but the VREG command is `0x02` + feature `0x02` + a non-zero action; the previous text had `0x02 0x02 0x01`. A reader could send two bytes and have the next command consumed as the action. **Fix:** "the host sends feature `0x02` with a non-zero action (`0x02 0x02 0x01`)" or restore the three-byte form.
2. **[minor] `edge-cases.md:15` still says "Entering binary from a mode \| pins, VREG and pull-ups reset".** The corrected #17 wording says AUX1 can remain low after binary entry; this overview row overgeneralises "pins". **Fix:** "BBIO1 pins, VREG and pull-ups reset; AUX1 is not touched" or add a cross-reference to `wiring.md` §Reset lines.
3. **[minor] `openocd.md:158` reads "VREG on only if the board powers target".** The missing article makes the new warning look clipped. **Fix:** "powers the target". This is style only.
